# Commodity Anomaly & Volatility Detection

This is a tool I built to catch unusual price and volatility behaviour in commodity markets —
gold, silver, and WTI crude oil — the kind of thing a risk team on a trading desk actually
wants a heads-up on. I built it end-to-end: pulled and cleaned the data myself, caught a
couple of real bugs along the way rather than shipping around them, and tested the results
against an independent method instead of just trusting the first approach that worked.

**Live demo:** https://commodity-anomaly-detection.streamlit.app/
**Repo:**https://github.com/Amol2772/commodity-anomaly-detection

## Why I built it this way

Trading desks need to know when a market is behaving abnormally — not necessarily to predict
what happens next, but to know when to pay closer attention. So the goal here wasn't "build
the most accurate trading model." It was: build something explainable that flags unusual days,
and be honest about what it can and can't do. That's also why there's a whole notebook
(`commodity_backtest.ipynb`) dedicated to the obvious next question — "okay, but could you
actually trade this?" — answered honestly, rather than dodged.

## What it actually found

The result I'm most confident about isn't a single number, it's an agreement between two
methods that had nothing to do with each other. I built a rolling z-score baseline to flag
unusual days, and separately built a SARIMAX forecasting model with no knowledge of those
flags at all. When I checked the forecast's error on the days my baseline had flagged versus
every other day, it was **4.6 to 4.8 times higher** — consistently, across all three
commodities. Two unrelated methods landing on the same "these days were weird" conclusion is a
much stronger result than either one succeeding on its own.

It also genuinely caught real events. The z-score baseline flagged the **January 30, 2026
precious-metals crash** (gold's worst day in over a decade, silver's by an even wider margin)
and **WTI crude's historic move into negative prices on April 20, 2020** — the first time
that had ever happened.

That second one came with a good story, actually. My first version of the return calculation
used log returns, which is the standard choice — except log returns are mathematically
undefined for a negative price, and WTI went negative that day. My code was silently deleting
the single most important data point in the whole dataset, and I didn't notice until a stray
`RuntimeWarning` tipped me off. I traced it back, switched to simple percentage returns
instead, and then went and checked that the day actually showed up in every downstream
detector afterward. Good reminder that a pipeline running without errors isn't the same thing
as a pipeline being correct.

strategy versus buy-and-hold, per commodity.

## How it works

| Stage | Approach |
|---|---|
| Data | Daily OHLCV for gold, silver, WTI crude (`yfinance`), 2015–present |
| Data hygiene | Simple returns, not log returns — required after finding WTI's 2020 negative price breaks log-return math |
| Anomaly baseline | Rolling z-score using median/MAD rather than mean/std — a plain std-based version got thrown off by extreme days for weeks afterward, masking real anomalies right behind them |
| Point anomalies | Isolation Forest on return + short/long volatility — catches combinations a single-feature z-score would miss |
| Regime detection | `ruptures` changepoint detection on a robust volatility signal |
| Forecasting baseline | SARIMAX with lagged volatility as an input, walk-forward validated — used purely as an independent check on the anomaly flags |
| Backtest | A simple fade-the-anomaly signal, non-overlapping trades, transaction costs included, parameters chosen on economic logic rather than tuned to look good |
| Dashboard | Streamlit — lets you explore each commodity's anomalies and compare across all three |

One thing worth mentioning: every notebook and the dashboard read their shared settings
(window length, threshold, etc.) from a single `project_config.py` file, rather than each one
hardcoding its own copy. That wasn't the original design — it came from an earlier version
where two notebooks quietly disagreed with each other because I'd only updated one of them.
Centralising it was the fix.

## Repository structure

```
├── project_config.py                    # shared parameters — single source of truth
├── download_commodity_data.py           # pulls & sanity-checks raw data
├── requirements.txt
├── data/                                # generated by the download script
├── commodity_eda.ipynb                  # exploratory analysis, data quality, z-score baseline
├── commodity_anomaly_detection.ipynb    # Isolation Forest + ruptures, benchmarked vs. baseline
├── commodity_forecast_baseline.ipynb    # SARIMAX independent validation
├── commodity_backtest.ipynb             # honest backtest of a simple derived signal
├── app.py                               # Streamlit dashboard
└── MODEL_CARD.md                        # intended use, limitations, governance framing
```

## Running it

```bash
pip install -r requirements.txt
python download_commodity_data.py        # populates data/
```

Then run the notebooks in the order listed above, or just launch the dashboard:

```bash
python -m streamlit run app.py
```

## What I'd flag as limitations, unprompted

- The backtest only has a few dozen trades per commodity over 11 years — enough to be
  interesting, not enough to be statistically confident about
- Transaction costs are a flat assumption, not a real execution model, and I haven't modelled
  borrow costs for the short side
- The SARIMAX order and the z-score threshold came from a documented sweep against known
  events, not an exhaustive search — a reasonable starting point, not a claim that they're optimal
- This is a portfolio project demonstrating a methodology, not a production system or
  investment advice — worth saying plainly rather than letting the dashboard imply otherwise
